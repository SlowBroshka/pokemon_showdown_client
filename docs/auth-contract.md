# Контракт нативной авторизации Showdown

Дата проверки: **25 октября 2026 года**. Задача: [#15](https://github.com/SlowBroshka/pokemon_showdown_client/issues/15).
Это результат исследования для C2, а не реализация входа в приложении.

## Решение и степень проверки

Для первого HTTP-адаптера выбираем
`POST https://play.pokemonshowdown.com/~~showdown/action.php`
с `act=login`, `name`, `pass`, `challstr` в form-urlencoded теле.
Это путь из проверенного официального клиента [C1, C2]. Пароль передаётся
только этому HTTPS-хосту. Адрес авторизации не выводится из введённого WSS-адреса.
На первом этапе вход поддерживается только для явно настроенного основного сервера
с `serverid=showdown`; произвольный WSS остаётся доступен для проверки подключения.

**Выбор предварительный до успешного входа тестовым зарегистрированным аккаунтом.**
Нативный Dart-клиент подтвердил WSS/challenge и ответы на пустые HTTP-запросы.
Это не доказывает успешный login, получение сессионной cookie или восстановление.
Приступать к HTTP-адаптеру можно с этим контрактом; объявлять вход совместимым
до выполнения оставшейся проверки нельзя.

| Проверка | Результат | Основание |
|---|---|---|
| Прямой WSS `wss://sim3.psim.us/showdown/websocket` | Получен `challstr` с разделителем `\|` | Выполнено нативным Dart-скриптом |
| POST `/~~showdown/action.php`, `act=login`, пустые name/pass | HTTP 200, text/plain, `]` + JSON, поле `actionerror`, без assertion | Выполнено; это отказ валидации, не неверный пароль существующего аккаунта |
| POST `/api/login`, пустые name/pass | HTTP 200, text/plain, `]` + JSON, поле `actionerror` | Выполнено; endpoint нельзя объявить неработающим |
| GET `/api/upkeep`, без cookies и без challenge | HTTP 200, `]` + JSON, ключи `assertion`, `loggedin`, `username`, assertion отсутствует/пуст | Выполнено; восстановление сессии не проверено |
| Set-Cookie в трёх указанных отказах/анонимных ответах | Не получен | Не характеризует успешный вход |
| Успешный login → `/trn` → `updateuser` | Не выполнено | Нужен согласованный тестовый аккаунт |
| Неверный пароль, истечение, authenticated upkeep/logout | Не выполнено | Требуют отдельной проверки с тестовой сессией |

Машиночитаемый результат: [auth-observations.json](auth-observations.json).
Повторить из корня: `dart run tool/auth_contract_probe.dart`.
Скрипт выполняет только анонимные сетевые проверки по явному запуску, не входит
в CI и запуск приложения. Challenge остаётся в памяти; в выводе нет его значения,
тел ответов, паролей, assertion и значений cookies. Сам скрипт не принимает пароль.
Результат содержит время UTC; для московского времени прибавить три часа.
HTTP-тело ограничено 64 КиБ; неожиданные типы флагов loggedin не выводятся как
произвольные данные, а отмечаются как `null`.

## Последовательность входа

1. Создать новое поколение WSS-соединения. Подписаться на глобальные события
   до подключения. Сбросить прежние challenge и ожидающую авторизацию.
2. Дождаться `ChallengeEvent`. В HTTP передавать весь его `challenge`, включая
   разделитель keyid/challenge, без внешнего `|challstr|`. Применять form encoding,
   а не склеивание строки. Не обрезать и не преобразовывать пароль.
3. Пользователь явно вводит имя и пароль существующего аккаунта. Отправить один
   POST в фиксированный auth endpoint. На старте не нужны браузерные cookies;
   фактическое поведение успешного ответа ещё проверяется. Redirect не выполнять.
4. Проверить HTTP-статус и ограничение размера, затем префикс `]`, затем JSON-объект.
   Не полагаться на Content-Type application/json: проверенные ответы text/plain.
   Для login требовать `curuser.loggedin == true`, непустой `curuser.username`
   и пригодный assertion. Это схема C2, ещё не запись успешного live-сеанса.
5. Сопоставить канонический userid введённого имени с username ответа.
   Для поддержанного на старте ASCII-имени userid = строчные `[a-z0-9]` без
   остальных символов; пустой userid отвергать. Не реализовывать догадки о
   транслитерации Unicode. Каноническое имя из ответа проходит валидацию команды.
6. Только если поколение соединения, текущий challenge и попытка входа всё ещё
   актуальны, отправить существующий `TrnCommand`: `|/trn NAME,0,ASSERTION`.
   Assertion непрозрачен для клиента: не разбирать подпись и не считать его
   долговременным токеном. Команда сохраняет запятые внутри assertion [S2, S3].
7. Ожидать глобальный `UpdateUserEvent` для того же userid с `named == true`
   в том же поколении после отправки `/trn`. Только тогда показать успешный вход.
   Один `named` не доказывает регистрацию: основание здесь — успешный password-login
   плюс подтверждение требуемой личности. HTTP 200 и отправка в сокет не достаточны.
8. При разрыве, отмене, новом challenge или завершении владельца инвалидировать
   попытку. Поздний HTTP-ответ не отправляет `/trn`. После разрыва автоматически
   не повторять парольный POST или `/trn`; нужен новый осознанный вход.

При сопоставлении `updateuser.user` отделить маркер ранга и хвост статуса `@...`
от имени; не включать статус в userid. Событие для другой личности не завершает
попытку и не продлевает её таймаут. Политику неподдерживаемых имён показывать явно.

В каждый момент разрешена одна попытка входа. До отправки `/trn` отмена только
инвалидирует попытку и поздний HTTP-ответ. После отправки `/trn` отмена или новый
challenge требуют отключения: в updateuser нет ID попытки, поэтому позднее
подтверждение нельзя надёжно отличить от ответа на следующий вход тем же именем.
Новую попытку разрешать после завершения отключения и нового challenge.

## Ошибки и локальная политика

| Условие | Будущая категория | Поведение |
|---|---|---|
| DNS/TLS/сетевая ошибка или таймаут | `network` / `timeout` | Нет автоматического повтора; разрешить явную попытку |
| HTTP 3xx | `unexpectedRedirect` | Не следовать, не пересылать секреты |
| HTTP 429 / 5xx | `rateLimited` / `serviceUnavailable` | Не называть неверным паролем |
| Остальной HTTP не 200 | `httpFailure` | Не разбирать как успешный вход |
| Пустое тело, HTML, нет `]`, неверный JSON/корень/типы | `invalidResponse` | Не отправлять `/trn` |
| `actionerror` или `error` со строкой | `loginRejected` | Даже при HTTP 200; исходный текст не писать в общий журнал |
| `curuser.loggedin == false` | `loginRejected` | Не выводить «неверный пароль» без установленного кода ошибки |
| Нет обязательных полей успеха / username не совпал | `invalidResponse` | Не отправлять `/trn` |
| Assertion пуст, содержит CR/LF/HTML, равен `;`, начинается `;;` | `invalidAssertion` | Не отправлять команду; специальные ответы не считать токеном |
| `nametaken` после `/trn` | `identityRejected` | Завершить попытку отказом; сервер отвергает и неверные/просроченные подписи |
| Нет подходящего updateuser за срок ожидания | `confirmationTimeout` | Считать личность неподтверждённой; отключить соединение перед новым входом |

Приоритет: HTTP → корректная оболочка/тип JSON → поля отказа → поля успеха.
Ответ с одновременно `error` и assertion не принимается. Неизвестные дополнительные
поля допускаются, неизвестные схемы успеха — нет. Это строгая политика нашего
клиента, а не обещание сервера о стабильности всех полей.

Предварительные ограничения адаптера: 15 секунд на HTTP, 10 секунд на подтверждение,
64 КиБ на HTTP-ответ; зависание на ожидании challenge также ограничить 10 секундами.
Это локальные настраиваемые пределы. Они не определяют срок действительности
assertion, который проверяет сервер [S2]. Не очищать/исправлять HTML и подпись
перед отправкой: нарушение формы означает отказ.

В серверном коде встречается `|nametaken||MESSAGE` при некорректном имени.
Наш текущий декодер требует непустой username и возвращает для этого
`MalformedServerEvent`. В PR контроллера авторизации нужно либо расширить модель
и тесты этого события, либо явно завершать активный вход безопасной ошибкой
на такую запись. Нельзя оставить пользователя бесконечно ожидающим подтверждения.

## Cookies, выход и хранение

В этом этапе пароль живёт только в памяти на время явного входа. Не сохранять его
в настройки, fixtures, Git, логи, ошибки или уведомления. После попытки очищать
поле/ссылки; Dart не гарантирует физическое обнуление памяти строки.
Assertion также не сохранять и не выводить через serialize/toString/сетевой журнал.

Успешный login может выдать cookie; точное имя, атрибуты, срок и возможность
использования нативным клиентом **не проверены**. Не придумывать cookie jar на
основе браузерного поведения. Для начального входа без сохранения не сохранять
Set-Cookie на диск и не обещать восстановление после закрытия приложения.
Документированный `/api/upkeep` возвращает другую схему (`loggedin` в корне),
его нельзя разбирать как ответ password-login с `curuser`.

Официальный клиент при logout вызывает HTTP `act=logout`, посылает WSS `/logout`
и отключается [C2]. Простое отключение закрывает локальную сессию, но не доказывает
отзыв HTTP-cookie. Кнопку полного выхода и cookie-инвалидацию реализовывать только
после проверки соответствующего потока. Восстановление, истечение и secure storage
остаются отдельным этапом C2/C10.

## Примеры и оставшаяся приёмка

Синтетические [HTTP-примеры](../test/fixtures/auth/http-responses.json) описывают
вход будущего декодера и ожидаемые категории. [Сценарии сессии](../test/fixtures/auth/session-scenarios.json)
задают порядок событий и гонки для будущего контроллера. Они не являются
автотестами ещё не написанной авторизации и не доказывают её работу на сервисе.
Схемы успешного ответа основаны на C2; отрицательные/повреждённые примеры намеренно
искусственные. Assertion `synthetic,...;not-a-signature` не имеет действительной
подписи. Не заменять его реальным токеном в Git.

Перед приёмкой работающего входа в PR 3–5 выполнить на согласованном аккаунте:

1. Password-login с настоящим challenge; зафиксировать только ключи/типы ответа
   и атрибуты cookies без значений. Проверить выбранный action.php endpoint.
2. Передать assertion тому же WSS, дождаться совпадающего updateuser; проверить
   начальное гостевое событие и отсутствие ложного успеха до подтверждения.
3. Неверный пароль и отказ имени; проверить категории без раскрытия ответа/секретов.
4. Разрыв во время HTTP, новый challenge, поздний ответ, повторное нажатие и
   таймаут подтверждения — на контролируемом сервере/адаптерах.
5. На Android/Linux повторить успешный вход и локальное отключение. Для будущего
   сохранения отдельно проверить cookie upkeep, истечение и полный logout.

Тестовый аккаунт/стенд в этой задаче не предоставлен; последние проверки не выполнены.
Публичный поиск боя и регистрация аккаунта для исследования не использовались.
