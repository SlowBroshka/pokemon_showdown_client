# Контроллер авторизации

Задача: [#21](https://github.com/SlowBroshka/pokemon_showdown_client/issues/21).
Четвёртый пункт C2, после [HTTP-клиента](auth-api-client.md) и [общей сессии](session.md).

## План и реализованный объём

Один PR: безопасные состояния → привязка HTTP/challenge к попытке и соединению
→ отправка `/trn` → подтверждение личности → отмена/отказы/таймауты → тесты.
Реализация: `lib/core/auth/auth_controller.dart`, без зависимости от Flutter.
[UI входа и переводы сообщений](auth-ui.md) реализованы следующим PR.
Сохранение сессии и reconnect остаются отдельными этапами. Живой вход аккаунтом не проверен.

## Владение и API

`MyApp` создаёт один AuthController на общую ShowdownSession **до подключения**.
При завершении закрывает контроллеры, затем сессию. Контроллер владеет своим
AuthApiClient (в том числе внедрённым), подпиской и таймерами, но не сессией.
Один API-клиент нельзя делить между несколькими контроллерами.

| API | Контракт |
|---|---|
| `state` | Неизменяемый AuthState: phase, error, подтверждённые username/userId |
| `changes` | Broadcast-уведомления без replay; начальное состояние читать через getter |
| `canLogin` | Готовность, доверенный сервер, отсутствие другой попытки/очистки |
| `login(username, password)` | Future завершается после подтверждения, отказа или инвалидирования попытки |
| `cancel()` | Отмена и ожидание локальной очистки текущей попытки |
| `dispose()` | Терминальное идемпотентное завершение без автоматического переподключения |

Обычные ошибки доступны в `state.error` как AuthFailure: UI не получает необработанных
исключений из login. Повторное нажатие или вызов при canLogin=false ничего не
отправляет. После отказа до `/trn` разрешена новая явная попытка, когда canLogin
снова true. Окончание очистки HTTP также публикует снимок для обновления кнопок.

Снимок не содержит пароля, assertion, challenge, HTTP-ответов и серверного текста.
toString выдаёт только фазу и код ошибки. Имя/userId присутствуют только в
authenticated. Challenge хранится в памяти до инвалидирования; пароль/assertion
не удерживаются в состоянии после HTTP-части. Завершение подписок — ответственность
подписчика; приостановленная подписка может задержать закрытие потока Dart.

Если контроллер создан после уже полученного challenge, прочитать старое событие
из broadcast-потока невозможно. Он дождётся нового challenge либо отключится
по таймауту. Поэтому штатный владелец создаёт контроллер заранее.

## Успешный путь и ограничения сервера

`disconnected → waitingChallenge → ready → authenticating → awaitingConfirmation
→ authenticated`. Ранний challenge во время handshake сохраняется, но canLogin
требует connected. Таймаут challenge — 10 секунд после установления соединения;
таймаут самого handshake отдельно контролирует транспорт.

Поддерживается только `wss://sim3.psim.us/showdown/websocket`, без query/fragment/
учётных данных, с отсутствующим портом либо явным 443. Другой WSS оставляет
диагностику подключения доступной, но авторизация получает unavailable/
unsupportedServer и не отправляет парольный HTTP-запрос.

Попытка получает ID, поколение соединения и ревизию challenge. После HTTP-ответа
все они проверяются повторно вместе со статусом и endpoint. Отправляется TrnCommand
с исходным assertion. Успех допускается только после глобального updateuser с
named=true и нужным userId. Маркер ранга и статус `@...` отделяются от имени;
поддерживается и старое написание USER без маркера ранга.

Другая личность, named=false и updateuser в комнате не подтверждают вход и не
продлевают срок ожидания. После подтверждения смена личности или named=false
снимают authenticated и отключают соединение. Один named без password-login
никогда не считается доказательством входа в аккаунт.

## Очереди, отмена и ошибки

`TransportUpdate.sequence` назначается на источнике до асинхронной доставки
и сохраняется через RoomRouterUpdate и SessionUpdate. Все строки одного принятого
WebSocket-сообщения имеют одинаковый sequence. `session.latestUpdateSequence`
показывает номер на источнике; `session.endpoint` — адрес последней принятой попытки.

Перед `/trn` контроллер даёт обработаться уже поставленным в очередь событиям,
повторно проверяет попытку/challenge/поколение и запоминает source sequence.
Подтверждение принимается только из более нового сообщения: ранее полученный,
но задержавшийся updateuser не должен дать ложный успех. Это локальная защита
от очередей, не криптографический ID транзакции. В updateuser ID попытки отсутствует,
поэтому одновременно допускается только один вход.

Новый challenge до `/trn` отменяет HTTP; явный повтор разрешён после очистки.
Новый challenge после `/trn`, отмена ожидания или таймаут подтверждения (10 секунд)
требуют отключения. Поздний updateuser не сможет подтвердить следующую попытку
в том же соединении. Автоматического повтора `/trn` нет.

HTTP-категории сохраняются из AuthApiClient. Дополнительные: unsupportedServer,
challengeTimeout, confirmationTimeout, identityRejected, connectionLost,
sendFailed, invalidServerEvent. Их ARB-сопоставление добавляется вместе с UI.
Глобальный nametaken для нужного имени либо с пустым именем завершает ожидание
отказом. Декодер теперь допускает пустой username; текст отказа остаётся непустым.
Глобальные error/popup после `/trn` также завершают вход безопасной категорией.
Сообщения других комнат и nametaken другого имени не приписываются попытке.
Повреждённый challenge или критичное событие подтверждения дают invalidServerEvent.

Отмена до `/trn` отменяет только HTTP, сохраняя общую WSS-сессию. Отмена/ошибка
отправки/неоднозначность после `/trn` отключают её. Закрытие владельца сессии
также инвалидирует попытку. Dispose контроллера до `/trn` не отключает сессию;
после `/trn` или подтверждения отключает, но не вызывает session.dispose.
Владелец по-прежнему может подключить её заново.

## Проверки и оставшаяся приёмка

`test/core/auth/auth_controller_test.dart` покрывает последовательность входа,
отказ/повтор, отсутствие ложного успеха по named, другие имена/комнаты, двойное
нажатие, ранний и заменённый challenge, очереди событий, отмену до/после `/trn`,
переподключение, таймауты, malformed-события и disposal. Метки sequence отдельно
проверяются в тестах сессии. Подготовленные session-scenarios.json отражены этими
тестами; сам JSON остаётся описанием сценариев, а не интерпретатором тестов.

Запуск: `flutter test --concurrency=1`. Управляемые HTTP/WebSocket-адаптеры
используют синтетические данные без публичной сети. **Успешный вход реальным
аккаунтом и приёмка Android/Linux ещё не выполнены.** После появления UI нужен
согласованный тестовый аккаунт для полного обмена и реальных отказов сервиса.
Cookie upkeep/logout и сохранение сессии не входят; отключение не обещает отзыва
HTTP-сессий.
