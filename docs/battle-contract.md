# Контракт минимального боя

Дата сверки: **25 октября 2026 года**. Первый PR этапа «Минимальный бой».
Задача: [#25](https://github.com/SlowBroshka/pokemon_showdown_client/issues/25).
Статус: реализованы [разбор request](battle-request.md) и
[минимальные события/состояние](battle-state.md),
[отправка решений](battle-decisions.md) и
[владение активной комнатой](battle-room-integration.md). [Экран боя и локальная приёмка](battle-ui.md) реализованы; публичный сервер не проверялся.

## Границы

Одна активная боевая комната, Gen 9 singles, два участника, один активный Pokémon
на сторону. Вход по ID заранее подготовленного боя. Контролируемый набор сценариев
для будущего Gen 9 Random Battle, а не полная поддержка этого формата.
Никаких сетевых действий или поиска соперника этот PR не выполняет.

В объём следующих PR входят атака, добровольная/вынужденная замена, терастализация,
ожидание, отказ выбора, HP/основной статус и результат. Поиск, challenge UI,
сдача, undo, таймер, reconnect, team preview, doubles, остальные поколения,
полный словарь, предметы/способности/погода/усиления и сложные механики — вне этапа.
При встрече неподдерживаемого изменения состояния прототип блокирует выбор.
Закрытие комнаты, отключение и потеря доступа не означают поражение.

5. [Сериализация выбора](https://github.com/smogon/pokemon-showdown-client/blob/ab4b77b8f3a5712e8fbe03ce106ef2b70a874fdb/play.pokemonshowdown.com/src/battle-choices.ts#L611) и [серверный разбор](https://github.com/smogon/pokemon-showdown/blob/9b136a8c8cdb860a8ab96fa063f906604e352547/sim/side.ts#L1269) — суффикс `terastallize`.

В SIM-PROTOCOL написано `terastalize`, но закреплённые исходники клиента и сервера
используют `terastallize`: выбираем второе. Это сверка исходников, не живая
проверка команды. Совместимость с текущим публичным сервером и полный реальный
бой на публичном сервере остаются отдельной приёмкой; локальная проверка этапа 6
описана в [battle-ui.md](battle-ui.md). Корпус написан вручную, не скопирован из реального боя;
он не содержит аккаунтов, секретов или записей чужих команд.

## Разделение ответственности

- C3: оболочка → типизированное событие/валидированный запрос; сборка команды.
- C5: последовательная проекция поля и отдельно последний приватный запрос;
  проверка действия, жизненный цикл решения и блокировки.
- C4/интеграция: `ConnectionController` владеет выбранной комнатой и её боевым
  контекстом. Подписка создаётся до `/join`; неожиданные комнаты получают `/leave`
  и не заменяют выбранную. [Жизненный цикл этапа 5](battle-room-integration.md).
- C6: отображение готовых моделей. Виджеты не читают сетевые строки.

Все модели на чистом Dart, отдельный класс/enum в отдельном файле. Существующая
`ShowdownSession` остаётся владельцем соединения. Миграция на Riverpod не требуется.
Состояние боя живёт выше экрана. Сетевые данные и приватный request не логируются
безусловно; сообщения об ошибках не включают весь входной пакет.

## Матрица событий

| Событие | Изменение проекции / правило |
|---|---|
| `init` / `title` / `deinit` | Создать контекст / обновить заголовок / закрыть комнату и запретить выбор |
| `player`, `teamsize`, `gametype`, `gen`, `tier` | Участники и метаданные; разрешены только gen=9, singles, стороны p1/p2. Tier — отображаемая строка, не доказательство поддержки |
| `start`, `turn` | Начало и номер хода; сами по себе не разрешают отправку решения |
| `switch`, `drag` | Активный Pokémon, раскрытые details и HP; не отождествлять вид с никнеймом |
| `move`, `cant` | Событие журнала; не рассчитывать урон и не уменьшать PP по догадке |
| `-damage`, `-heal`, `-sethp` | Применить сообщённый HP (у `-sethp` возможны две пары); сохранить масштаб и источник точности |
| `-status`, `-curestatus` | Основной статус: brn/par/psn/tox/slp/frz; не вычислять скрытые счётчики |
| `faint` | Обморок, HP=0; смена только по следующему request |
| `-terastallize` | Раскрытый Tera Type; не вычислять прочие эффекты механики |
| `request` | Заменить запрос и черновик; обновить приватные сведения своей стороны |
| `error` | Отказ/ошибка выбора по правилам ниже; чужая комната не влияет на решение |
| `win`, `tie` | Терминальный результат, очистка запроса и отключение действий |

HP своей команды из `side.pokemon.condition` хранить отдельно от публичного HP.
Например, `200/300 par` — собственные числовые HP/статус, а `50/100` противника —
шкала наблюдения, не утверждение о его максимальном HP. `0 fnt` означает обморок.
Неизвестные item/ability отличаются от явно пустых; не дополнять из справочника.
Идентификатор слота команды — индекс в текущем `side.pokemon`, не имя Pokémon.

Известные декоративные/метаданные (`|`, `t:`, `seed`, `rated`, `rule`, `clearpoke`,
`poke`, `teampreview`, `upkeep`, `inactive`, `inactiveoff`, `c`, `c:`, `j`, `l`,
`n`, `chat`, `join`, `leave`, `name`, `message`, `-message`, `-hint`, `-anim`,
`-crit`, `-supereffective`, `-resisted`, `-miss`, `-fail`, `-immune`, `-notarget`)
не разрешают действия; пропускаются/отображаются как текст. `teampreview` также
помечает неподдерживаемый режим. HTML/uhtml/uhtmlchange не исполняются: заглушка.
Любое иное неподдерживаемое боевое событие (например, `-transform`, `-boost`)
или повреждённое значимое событие ставит липкую блокировку `unsupportedState`:
свежий request её не снимает. Это консервативная политика нашего прототипа,
а не требование сервера. Снимается только новым контекстом боя.

## Контракт request

Вид запроса определяется сетевыми признаками, `requestType` не обязателен:

| Форма | Результат и доступные действия |
|---|---|
| JSON `null` | Очистить запрос, `noRequest`; никаких действий |
| `wait: true` | `wait`; side/active не обязательны, никаких действий |
| `forceSwitch: [true]` | `switch`; только живой неактивный слот своей команды |
| `active: [{moves: ...}]` + `side` | `move`; доступная атака или разрешённая замена |
| `teamPreview: true`, несколько активных слотов, ally | `unsupportedRequest`, действий нет |
| Невалидный JSON/типы/противоречащие признаки | `malformedRequest`, действий нет |

Политика валидации клиента: не приводить строки к числам/boolean; `rqid`, если
дан, — неотрицательное целое. Для действующего запроса side.id — p1/p2,
side.pokemon — 1–6 записей; обязательны ident/details/condition/active.
В move ровно один активный живой Pokémon; forceSwitch допускает активного fainted.
Проверять диапазоны HP, слоты и согласованность стороны; невалидная запись
блокирует весь запрос. `forceSwitch: [false]` — неподдерживаемый невыбираемый
запрос этого этапа. Пустая строка после `request|` — malformed, не JSON null.

У атаки обязательны сетевые `move`, `id`, `target`; для обычной атаки — целые
`0 <= pp <= maxpp`, maxpp > 0; disabled по умолчанию false. Пустой набор атак
не поддержан. Struggle допускается как явно присланная единственная атака
`id: struggle`, без PP; не синтезировать её из локального справочника.
Обычные атаки с pp=0 или disabled=true недоступны. Для singles поддержаны цели
normal/self/adjacentFoe/allAdjacentFoes/allAdjacent/any/randomNormal/all/allySide/
foeSide/allyTeam; неизвестная цель блокирует запрос, ручной выбор цели вне этапа.

`trapped: true` запрещает добровольную замену. `maybeTrapped` не означает запрета:
окончательное решение принимает сервер. Слот замены — живой и неактивный.
`canTerastallize` — непустое имя типа, разрешающее модификатор только атаки;
отсутствие/false означает недоступность. Иные активные специальные механики
(Mega/Z/Dynamax/Ultra) блокируют запрос как неподдерживаемый. `noCancel` хранится,
но undo в прототипе недоступен независимо от его значения.
Флаги `side.pokemon[].reviving` и `commanding` также блокируют запрос: семантика
выбора отличается от обычной замены. Подробности — в [API декодера](battle-request.md).
Неизвестные дополнительные JSON-поля сохранять/игнорировать без поломки известных
форм; известный неподдерживаемый режим не принимать за обычную атаку.

## Версия запроса, команды и подтверждение

Контекст решения: `(roomId, connectionEpoch, requestRevision, rqid?)` плюс
локальная идентичность экземпляра контроллера (contextToken), защищающая повторный
вход в тот же бой в одном соединении.
`requestRevision` — локальный монотонный номер каждой доставки request, включая
повтор с тем же rqid, null и ошибочный запрос. Он не передаётся серверу.
Выбор захватывает контекст; непосредственно перед отправкой он сверяется вновь.
Последовательность источника сессии также защищает от уже полученного, но ещё
не доставленного подписчику обновления. Конец боя/разрыв/закрытие блокируют send.

| Действие | Полное WebSocket-сообщение для rqid=7 |
|---|---|
| Атака, слот 1 | `battle-contract-1|/choose move 1|7` |
| Замена, слот 2 | `battle-contract-1|/choose switch 2|7` |
| Атака с Tera | `battle-contract-1|/choose move 1 terastallize|7` |

Без rqid суффикс `|7` полностью отсутствует. Номера слотов с единицы, они относятся
к текущему request. Не отправлять локализованные названия или произвольный текст.
Проверять roomId, разделители и переводы строк; никаких составных choices.

После send — `submitted`, кнопки отключены, это **не подтверждение принятия**.
Повторное нажатие не отправляет вторую команду. Свежий request сбрасывает черновик
и определяет следующие действия; wait не считается универсальным ACK.
`[Invalid choice]` после отправки в текущей комнате разрешает исправить актуальный
запрос; `[Unavailable choice]` переводит в `awaitingRequest` до нового request.
Ошибка без привязки к текущей отправке не открывает кнопки. В error нет rqid:
при неоднозначности принадлежности (например, после смены запроса) не разблокировать
отправку по старой ошибке. Неизвестный отказ после send оставляет выбор заблокированным.
Таймаут не запускает повторную отправку: показать неопределённый результат.

Disconnect делает данные stale, удаляет готовое решение и запрещает автоповтор.
Новые соединение/комната не используют прежний запрос. Неподдерживаемый/повреждённый
request запрещает выбор до следующего корректного, но липкая ошибка поля сохраняется.
`win`/`tie` терминальны: поздний request не возобновляет завершённый бой.

## Корпус и приёмка

[requests.json](../test/fixtures/battle/requests.json) содержит отдельные payload
и ожидаемую классификацию/доступные действия.
[scenarios.json](../test/fixtures/battle/scenarios.json) содержит упорядоченные
шаги, сообщения, ожидаемые изменения и команды. Формат описан в
[README корпуса](../test/fixtures/battle/README.md). Все 25 примеров requests.json
теперь проверяются тестами декодера. Ожидания scenarios.json остаются спецификацией
будущих тестов контроллера. Reducer проверяет проекцию пяти сценариев; полный
интерпретатор сценариев с choose/send ещё не реализован.

Приёмка PR 1: валидный JSON, уникальные ID, разрешимые ссылки, согласованная матрица
вход → состояние → действие и подтверждённые исходниками команды. Следующие PR
подключают эти файлы к настоящим тестам декодера, reducer и контроллера, не заменяя
проверки чтением заранее записанного expected. Обычные CI-проверки сохраняются.

Перед живой приёмкой PR 6 нужен согласованный тестовый бой/сервер; публичный
matchmaking не используется как автоматический тест. Проверить целиком обычный
ход, замену, Tera, отказ, завершение и разрыв на Android/Linux. Ограничения корпуса
и отсутствие полной поддержки Random Battle должны оставаться видимыми.
