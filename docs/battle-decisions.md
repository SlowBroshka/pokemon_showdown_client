# Этап 4: команды и контроллер решений

Задача #31, один PR после разбора request и минимального состояния боя.

## План реализации

1. Типизированные `/choose move`, `/choose switch`, суффикс `terastallize` и rqid.
2. Контроллер одной комнаты и одного поколения общей ShowdownSession.
3. Захват контекста выбора и повторная проверка непосредственно перед отправкой.
4. Обработка отказов, новой версии request, разрыва и неопределённой отправки.
5. Тесты через синтетический сокет, документация и проверки всего проекта.

Все пять задач реализованы. [Владение активной комнатой](battle-room-integration.md) реализовано в этапе 5;
экран боя и живая сквозная приёмка — этап 6.

## API и жизненный цикл

Создать `BattleDecisionController(session: session, roomId: roomId)` после начала
соединения, **до** получения init комнаты. События не переигрываются. Контроллер
не подключается сам, не выполняет join и не владеет сессией. Он применяет
`reduceBattleEvent` и предоставляет неизменяемый `state`, `phase`, `canChoose`
и поток `changes` без повторной выдачи истории.

`capture(BattleChoice.move(1))` возвращает nullable CapturedBattleChoice.
Для Tera используется `BattleChoice.move(1, terastallize: true)`, для замены —
`BattleChoice.switchTo(2)`. Это позиции в текущем request, начиная с единицы.
Сохранённый выбор можно передать `submit(captured)` после асинхронной работы UI.
Контроллер заново проверит принадлежность захвата своему экземпляру (contextToken),
комнату, поколение, локальную revision, rqid,
доступность действия, актуальность входящего потока и отсутствие отправки.
Даже одинаковый rqid нового request инвалидирует старый захват.

`submit == true` означает только успешную запись в сокет. `false` не разрешает
автоматический повтор: после ошибки записи phase может стать uncertain.
`phase == ready` также не является разрешением: использовать `canChoose` и
результат capture/submit. До init/start, при wait/null/невалидном request,
несовместимом состоянии или завершении боя выбор недоступен.

`dispose` освобождает подписку и таймеры; общая сессия остаётся открыта.
Разрыв или смена поколения делает состояние stale навсегда. Для следующего
соединения нужен новый контроллер, созданный до событий новой комнаты.

## Порядок событий и отказы

Источник увеличивает sequence до асинхронной доставки. Отправка запрещена,
если контроллер ещё не обработал текущую sequence. Все строки одного сетевого
сообщения имеют общую sequence, поэтому разрешение дополнительно откладывается
до следующего оборота event loop. Таймер отменяется и назначается заново при
каждом обновлении; submit всегда проверяет актуальный source watermark.
Пустой кадр передаёт служебный `emptyFrame` через router/session updates, чтобы
продвинуть watermark. В нём status/event/roomId равны null; фильтрованные потоки
протокольных событий его не содержат.

После отправки phase=submitted и повторное нажатие блокируется. Новый request
полностью заменяет прежний, отменяет таймер и снимает локальный статус отправки;
это не подтверждение принятия предыдущего решения. `wait` не означает ACK.

`[Invalid choice]` при единственной однозначно ожидаемой отправке разрешает
исправить выбор текущего request. `[Unavailable choice]` переводит в
awaitingRequest. Ошибки другой комнаты, popup и обычный текст этого не делают.
Ошибки сервера не содержат rqid: если отправку уже сменил новый request,
связать позднюю ошибку со следующей отправкой надёжно нельзя. После такого
случая контроллер консервативно трактует ошибки выбора как awaitingRequest
до конца своей жизни. Это может блокировать исправление допустимого выбора
до нового request, зато не разрешает повтор по ошибке от старого хода.
Неожидаемая ошибка без outstanding-отправки не меняет разрешение выбора.

Таймаут (по умолчанию 30 секунд) и ошибка записи дают uncertain. Разрыв затем
переводит в inactive/stale. Автоматических повторов, undo, forfeit и восстановления
после reconnect нет. Сырые ошибки сервера не сохраняются в контроллере.

## Проверки и границы

29 тестов команд/контроллера проверяют сериализацию и защиту полей, позиции,
Tera, trapped, forced switch, отсутствие rqid, повторное нажатие, смену revision,
отказы, терминальные состояния, задержанную доставку и несколько request в одном
кадре, пустые кадры, таймаут, ошибку сокета, reconnect и освобождение ресурсов.
Используются request fixtures этапа 1; это отдельные исполняемые сценарии тестов,
а не полный интерпретатор всех записей scenarios.json. Публичный сервер и живой
бой не использовались. ConnectionController теперь владеет выбранным боевым
контекстом; неожиданные комнаты не заменяют его. См. [этап 5](battle-room-integration.md).
