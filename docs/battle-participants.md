## Подробный план до реализации

1. Разделить активную позицию, публичное появление и слот приватного запроса.
2. Ввести неизменяемый реестр наблюдений с локальными ID. Сохранять покинувшие поле
   появления; совпадение клички/внешнего вида считать только подсказкой, не личностью.
3. Связать активные HP, статус, обморок и Tera с текущим появлением. Ограничить
   историю, сохраняя активных участников и явно отмечая усечение.
4. Добавить отдельную приватную ссылку на слот конкретной версии request, без
   копирования приватного состава, точных HP, предметов и способностей в реестр.
5. Обработать адресованные запасным сообщения снятия статуса; сохранить
   неоднозначность имени и не менять исторические данные произвольного участника.
6. Проверить замены/возвращение, одинаковые клички, p1/p2, лечение запасных,
   перестановку приватных слотов, неизменяемость, лимиты и изоляцию комнаты/epoch.
7. Обновить исполняемый корпус и матрицу, выполнить анализ и регрессии, открыть PR.

## Модель и публичный API

`BattleState.roster` — единственный источник активной публичной проекции;
`BattleState.active` сохранён как неизменяемое вычисляемое представление для
существующего UI. Конструктор/copyWith больше не принимает отдельную `active` map:
параллельные изменяемые копии поля и реестра исключены.

| Тип / поле | Значение |
| --- | --- |
| `BattleRoster.appearances` | Наблюдения по ID появления, включая исторические |
| `BattleRoster.activeIds` | Соответствие стороны p1/p2 текущему появлению singles |
| `BattleAppearance.id` | Монотонный номер внутри комнаты и epoch; не сетевой ID |
| `enteredTurn` | Ход появления на поле |
| `pokemon` | Последние публичные сведения этого появления |
| `samePresentationIds` | Сохранённые прошлые появления с точным совпадением ident/details |
| `benchStatuses` | Адресованные сообщения о снятии статуса запасного Pokémon |
| `historyTruncated` | Из истории уже удалялись записи из-за лимита |
| `privateActiveReference` | Отдельная ссылка revision + private side + slot → current appearance |

Каждый switch/drag создаёт новое появление. Даже единственное совпадение
`samePresentationIds` не доказывает, что это тот же Pokémon: маскировка ещё может
быть не раскрыта. Отсутствие совпадений тоже не доказывает нового члена команды.
Данные между появлениями не сливаются. Например, Tera/статус старого появления
не переносятся в новое без сообщения сервера. Различающиеся формы/details не
нормализуются по предположению.

**Число появлений не является числом уникальных или раскрытых членов команды.**
`teamSizes` сохраняет отдельное значение сервера; скрытые места реестром не
заполняются. Устойчивое сопоставление личности после Illusion/Transform и изменений
форм остаётся PR 6. На этом шаге сохраняется доказательная база без ложного слияния.

HP/status/Tera/faint обновляют только текущее появление. После ухода его snapshot
исторический: это не актуальное состояние запасного Pokémon. Предыдущие экземпляры
BattleState и их вложенные коллекции не меняются. Двухцелевой sethp проверяется
целиком до изменения реестра. Журнал действий дополнен `actorAppearanceId`, чтобы
одинаковые клички не теряли связь с появлением.

## Запасные участники и неоднозначность

`-curestatus|p1: Name|par` сохраняет `BenchStatusObservation`: буквальный адрес,
ход, снятый статус, `cured=true` и ссылки на сохранённые неактивные появления
той же стороны с такой кличкой. Активное появление кандидатом не считается.

Это адресованное свидетельство; даже один кандидат не исключает ранее невидимого
участника с тем же именем (`mayReferToUnseenPokemon=true`). Поэтому не выбирается
случайная запись, не меняются исторические HP/статус, не создаётся Pokémon с
выдуманным видом и не корректируется приватный request. Пустой список кандидатов
не означает ошибку протокола или раскрытие состава. Возвращение на поле даёт новый
публичный HP/status snapshot.

## Приватная ссылка и решения

При move/switch request ссылка создаётся только если его сторона имеет публичное
активное появление и ровно один слот снимка помечен active. Соединение делается
по стороне и активной позиции, а не совпадению клички/вида: приватное имя может
отличаться от маскировки. Это связь двух одновременных представлений, не доказательство
тождественности всех прошлых появлений.

Каждый request, включая повторный rqid, заменяет ссылку новой revision.
Смена своей активной позиции, wait/null/повреждённый request, несовместимость,
разрыв и завершение очищают её. Замена противоположной стороны свою ссылку
не уничтожает. Без публичного появления или при нескольких active-флагах связь
не создаётся. Приватный состав не используется для заполнения публичного реестра.

Ссылка не разрешает действия. Источником допустимых move/switch слотов остаётся
актуальный request, а отправку по-прежнему охраняет BattleDecisionController.
Сохранённый `privateSide` остаётся историческим приватным снимком, даже если ссылка
уже отозвана. Это не синхронизация его HP с публичными событиями.

## Ограничения памяти и жизненный цикл

Хранятся максимум 128 появлений и 128 сообщений о запасных участниках. При
переполнении удаляются старейшие неактивные появления; обе активные позиции
сохраняются. Ссылки кандидатов на удалённые записи отфильтровываются, а
`historyTruncated` остаётся true. ID не переиспользуются. Более старый журнал
действий может ссылаться на уже удалённый ID: потребитель не должен считать
наличие соответствующего snapshot гарантированным.

Состояние относится к комнате и connection epoch. Чужие события и старое
соединение не изменяют реестр. Разрыв сохраняет историю, но помечает бой stale;
новая сессия сама по себе не восстанавливает этот бой. Терминальное состояние
не принимает поздние изменения. Reconnect и восстановление истории здесь
не реализуются.

## Проверки

- Модульные проверки `battle_participants_test.dart`: замены/возвращение,
  одинаковые имена на одной/разных сторонах, атомарность HP, обморок/Tera,
  активное и запасное снятие статуса, неизвестные/неоднозначные адресаты.
- Приватные проверки: изменение порядка слотов, p2, отличающиеся скрытые
  имя/вид/HP, отсутствие или несколько active, очистка ссылок без утечки состава.
- Неизменяемость вложенных коллекций, ограничения памяти и очистка ссылок,
  чужие комнаты/epoch, stale/terminal, сохранение защит неизвестных событий.
- Семь исполняемых wire-сценариев в `participant_scenarios.json` используют
  настоящий контроллер и проверяют исходящую команду после сообщения о запасном.

```sh
flutter test test/core/battle test/core/protocol
flutter analyze
flutter test
dart format --output=none --set-exit-if-changed .
```

Отображение расширенного состава/статусов и новых меток в UI относится к PR 8.
Существующий экран продолжает читать `state.active`. Живая приёмка полного
случайного боя и публичная совместимость этим PR не заявляются.
