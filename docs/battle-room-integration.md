# Этап 5: владелец активной боевой комнаты

Обновление C4: владение перенесено в [RoomOwner](matched-room-owner.md);
ConnectionController сохраняет совместимый API экрана. Ниже — описание исходного этапа.

Задача #33. Один PR интеграции после команд и контроллера решений.

## План

1. Подключить BattleDecisionController к единственному владельцу выбранной комнаты.
2. Создавать подписку до /join и подтверждать тип комнаты по init.
3. Согласовать leave, deinit, disconnect, reconnect и повторный вход.
4. Передавать изменения боя владельцу экрана и освобождать ресурсы.
5. Проверить жизненный цикл и регрессии чатов на синтетическом транспорте.

Реализованы все пять задач. [Экран боя и локальная приёмка](battle-ui.md) реализованы в этапе 6.

## Владение и API

`MyApp` уже создаёт одну ShowdownSession, AuthController и ConnectionController
выше ConnectionScreen. Теперь ConnectionController также владеет боевым
контекстом. Дополнительный сокет и отдельный владелец комнаты не создаются.
Экран с переданным контроллером не уничтожает его при снятии с дерева виджетов.

`join(id)` — единый вход для чатов и боёв. До отправки команды создаётся
BattleDecisionController, подписанный на общую сессию. Поэтому init, метаданные,
start и request из одного первого пакета не теряются. Префикс ID не определяет
тип: только `init|battle` делает контекст доступным через `controller.battle`.
При другом типе временный боевой контроллер освобождается.

Будущий экран читает `controller.battle?.state`, phase и canChoose. Для решения
используются capture/submit из [API этапа 4](battle-decisions.md). Изменения боя,
включая готовность после обработки пакета и отправку решения, вызывают
notifyListeners у владельца комнаты. Сырые строки протокола экрану не нужны.

Разрешена одна выбранная или ожидаемая комната. Повторный join блокируется,
пока комната активна либо ожидается подтверждение. Неожиданные init, включая
другой бой, получают /leave и не меняют выбранный контекст. Это согласованная
политика одного владельца: вход по явному ID заранее подготовленного боя,
без автоматического принятия приглашений и без поиска соперника.

## Жизненный цикл

| Ситуация | Поведение |
|---|---|
| Ожидание init | battle=null; контекст уже подписан, но не предоставлен экрану |
| init выбранного боя | Контекст становится доступен; решение разрешается только после всех проверок этапа 4 |
| Повторный init того же типа | Сохраняются экземпляр, requestRevision и текущая операция leave |
| Повторный init с другим типом | Отключение; тип выбранной комнаты не подменяется |
| leave | stopChoosing синхронно и навсегда отзывает разрешение отправки до /leave; ожидается deinit |
| deinit | room очищается; контекст сохраняется с фазой closed и известным результатом; новый join разрешён |
| win/tie | Результат сохраняется; поздние request не возобновляют выбор |
| disconnect / потеря сети | Снимок остаётся stale, request очищается; автоматического повторения решения нет |
| Новый connect | Старый контекст освобождается; нет автоматического join |
| Следующий join | Старый контекст освобождается, новый подписывается до отправки команды |
| Отказ/таймаут join | Отключение и освобождение неподтверждённого контекста |
| dispose владельца | Решения запрещаются сразу, подписки/таймеры освобождаются; injected session остаётся у вызывающего |

`battle` может быть ненулевым после deinit или разрыва, когда активной комнаты
уже нет: это сохранённый контекст для результата/устаревшего снимка. Он не даёт
разрешения отправки. Результат без win/tie не выдумывается; выход не означает
поражение. Сохраняется только последний контекст, до следующего join/connect.
`closed` владельца позволяет дождаться освобождения ресурсов при завершении приложения.

`stopChoosing()` оставляет приём событий включённым: результат, пришедший после
нажатия выхода, ещё может попасть в снимок до deinit. Новый request не снимает
этот запрет. Возобновить разрешение можно только созданием нового контекста.

## Защита повторного входа

В одной сессии можно выйти и снова войти в тот же roomId. Тогда connectionEpoch,
rqid и локальная requestRevision могут совпасть с прошлым посещением. Поэтому
CapturedBattleChoice дополнительно содержит непрозрачный contextToken экземпляра
контроллера. capture назначает его, submit проверяет идентичность. Старый захват
нельзя использовать в новом контроллере даже при совпадении остальных полей.
Токен локальный, не сериализуется и не отправляется серверу.

## Проверки и ограничения

19 интеграционных тестов проверяют первый пакет и общую сессию, определение типа,
обычный чат, чужие комнаты/события, повторный init, синхронный запрет при leave,
результат и закрытие без результата, повторный вход, разрыв/reconnect,
уведомления, ошибку join/leave, таймаут и освобождение ресурсов. Отдельный widget-тест
проверяет, что снятие экрана не уничтожает контекст: он продолжает принимать события
на том же соединении. Сохраняются проверки команд, контроллера решений и чатов.

Публичный сервер не использовался. Экран теперь показывает состояние и кнопки боя; результаты локальной проверки
находятся в [документации этапа 6](battle-ui.md).
Поддержка ограничена контрактом Gen 9 singles и распознанными событиями:
неподдерживаемая механика по-прежнему блокирует выбор.
