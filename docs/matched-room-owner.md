# Единый владелец комнаты: план и API четвёртого PR

Дата: **29 октября 2026 года**. Задача [#43](https://github.com/SlowBroshka/pokemon_showdown_client/issues/43).
Основа: [контракт поиска](matchmaking-contract.md), [протокол](search-protocol.md),
[предыдущая интеграция комнаты](battle-room-integration.md).

## План и результат

1. Выделить владение комнатой и боем из ConnectionController в RoomOwner,
   сохранить совместимый API существующего экрана.
2. Резервировать единственного владельца до поиска, проверяя baseline, личность
   и поколение соединения; исключить одновременный ручной вход.
3. Принимать найденный бой только после games, init и подтверждения своей стороны.
4. Доставлять начальные и последующие события одним путём, без потери или
   повторного применения первого request.
5. Ограничить накопление кандидата, запретить подмену активного боя, обработать
   конфликт, смену личности, разрыв и немедленное новое подключение.
6. Проверить старые сценарии и новые переходы, описать API для PR 5.

Пункты реализованы. RoomOwner находится в features/rooms: он использует существующие
ChangeNotifier и ConnectionMessage, остаётся компонентом приложения. Общая сессия
и протокольные модели остаются в core. Контроллер поиска и UI поиска не добавлены.

## Владение и совместимость

ConnectionController управляет подключением, проверяет адрес, при необходимости
владеет ShowdownSession и предоставляет `rooms`. Getters room/battle/joiningId,
методы join/leave и уведомления делегируются единственному RoomOwner. Экран
не создаёт второго владельца и не меняет API.

RoomOwner создаётся до подключения. Он владеет выбранной комнатой, операцией
join/leave, резервированием поиска и одним BattleDecisionController. Dispose
отменяет собственные подписки/таймеры; `closed` ждёт освобождения ресурсов.
Сессию RoomOwner никогда не уничтожает. Результат/устаревший снимок боя сохраняется
при выходе/разрыве по прежним правилам; новый контекст освобождает прежний.

Вне резервирования неожиданный init по-прежнему получает leave. Во время
резервирования найденный кандидат не получает автоматический join/leave/forfeit.
Конфликт второго кандидата блокирует принятие, а не заменяет первый бой.
Явная пользовательская команда leave остаётся доступной для выбранной комнаты.

## API резервирования

`reserveSearch(userId:, connectionEpoch:, baseline:)` возвращает непрозрачный
Object token либо null. Метод не отправляет сетевых команд. Предусловия:

- connected, актуальный epoch, нет выбранной комнаты, join/leave или резервирования;
- userId канонический и совпадает с последним named updateuser этой сессии;
- baseline — тот же экземпляр, что в `rooms.searchBaseline`, полученный из
  последнего корректного глобального updatesearch; поиски и игры пусты;
- источник не продвинулся вперёд обработанных событий, завершена доставка frame.

Named не доказывает регистрацию/авторизацию. **PR 5 обязан дополнительно проверить
AuthController, свежий каталог, разрешённый экспериментальный режим и собственную
попытку поиска** перед резервированием и непосредственно перед отправкой.
Контроллер поиска получает тот же `ConnectionController.rooms`, а не создаёт новый.

`releaseSearch(token)` разрешён только в фазе reserved, без кандидата, в актуальном
соединении и с тем же token. Старый callback не освобождает новое резервирование.
**Обязанность вызывающего кода:** использовать release только для ещё не отправленного
или доказанно завершённого поиска. Сам token не доказывает отсутствие серверной
операции. Нажатие отмены, пустой updatesearch и таймаут НЕ дают права освобождать
резервирование. Состояние outcomeUnknown не позволяет снять его через release;
восстановление проходит через отключение и новую проверку сессии.

RoomHandoffPhase — состояние принятия комнаты, не состояния очереди:

| Фаза | Значение |
|---|---|
| idle | Нет резервирования |
| reserved | Владелец занят будущим поиском, кандидата пока нет |
| awaitingEvidence | Есть один кандидат, ждём остальные свидетельства |
| adopted | Комната принята и опубликован battle |
| outcomeUnknown | Конфликт/ошибка, новые комнаты и решения заблокированы |

`candidateRoomId` — диагностический кандидат, не готовый активный бой. Состояние
публикуется через ChangeNotifier. Сам RoomOwner не показывает локализованные тексты
нового поиска; ошибки пока используют существующий безопасный serverNotice.

## Подтверждение и доставка

Кандидат выбирается из единственной записи games либо init|battle во время
резервирования. ID должен быть допустимым battle-ID. Несколько игр, иной тип игры
или второй init другой комнаты дают outcomeUnknown. Пустой снимок не отменяет
резервирование; отсутствие searching не интерпретируется как ACK.

Для принятия требуются games с тем же ID, init|battle и собственная сторона p1/p2:
либо player с именем текущего пользователя, либо приватный request с именем своей
side. Если доступны оба источника, их стороны и имена должны согласовываться.
Неизвестная личность не подставляется из названия комнаты. Позднее изменение своей
стороны или личности отзывает разрешение решений. Неподдержанные механики блокирует
боевой слой; уже найденный бой при этом не становится поводом для нового поиска.

RoomOwner заранее слушает единый session.updates. BattleDecisionController получил
необязательный параметр `updates`: владелец передаёт через него свой синхронный
поток, поэтому контроллер не подписывается ещё раз на сессию. Прямые потребители
без updates сохраняют прежнюю подписку. Источник соединения и проверки отправки
по-прежнему берутся из настоящей ShowdownSession; подмена сетевого транспорта
этим параметром не выполняется.

До подтверждения события комнаты буферизуются. При принятии новый контроллер
получает буфер ровно один раз, затем последующие события через тот же поток.
Если принятие произошло на глобальном games после init, ему также передаётся
текущий глобальный update для продвижения sequence. Поле и первый request
доступны без повторного join. Барьер завершения frame в боевом контроллере
сохраняется: промежуточное подтверждение не позволяет отправить ход раньше
последующих событий того же пакета. Повтор init не создаёт второго контроллера.

## Ограничения и ошибки

Не более 256 событий и 256 KiB суммы UTF-8 размеров исходных строк событий
(без заголовков комнат/разделителей транспорта). При превышении любого лимита
буфер очищается, выставляется outcomeUnknown. Таймаут handoffTimeout, по умолчанию
10 секунд, запускается при первом кандидате, не продлевается новыми сообщениями.
Он не ограничивает длительность поиска до появления кандидата.

Повреждённый updatesearch во время резервирования, malformed-событие кандидата,
deinit до принятия, противоречивая личность, конфликт или таймаут блокируют
принятие. У уже выбранного боя при конфликте отзываются захваченные решения,
но он не заменяется и может получить завершающую историю/результат.

Новый connecting сам очищает прежнее резервирование/контекст: при немедленном
переподключении старый disconnected может быть отброшен проверкой epoch до
доставки владельцу. Старые события/токены не могут принять комнату нового соединения.
Никаких повторов search/choose после разрыва нет.
