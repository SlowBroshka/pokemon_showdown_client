# Приёмка поиска боя: седьмой PR

Дата: **30 октября 2026 года**. Задача [#49](https://github.com/SlowBroshka/pokemon_showdown_client/issues/49).
Основа: [контракт](matchmaking-contract.md), [контроллер](matchmaking-controller.md),
[UI](matchmaking-ui.md). Это завершение локального этапа поиска, не разрешение
на полноценную публичную игру: механики Random Battle пока поддерживаются частично.

## План до реализации

1. Поднять полный сервер из закреплённой ревизии в отдельном временном каталоге.
   Старый `local_battle_server.cjs` проверяет движок и не заменяет matchmaking.
2. Добавить явно включаемую локальную тестовую личность без паролей и изменения
   публичной авторизации. Закрыть её в обычных/release-сборках и на публичном endpoint.
3. Соединить два клиента настоящими WebSocket: очередь, найденная комната,
   однократная доставка первого приватного request, отсутствие лишних join/leave.
4. Проверить раннюю отмену вокруг реальной подготовки команды, позднюю очередь,
   неопределённый исход, переподключение, повторный поиск и два соединения аккаунта.
5. Пройти интерфейс поиска до BattlePanel на Linux и Android-эмуляторе.
6. Прогнать регрессии и оформить воспроизводимый отчёт с границами доказанного.

## Стенд и границы вмешательства

`tool/local_matchmaking_server.cjs` экспортирует через `git archive` только файлы
ревизии Showdown `b354a81f11003a03f0dcd1dafd4edc641e6763bd`, использует установленные
`node_modules` исходного checkout и заново собирает сервер. Локальные конфиги,
состояние пользователя и старый `dist` не копируются. Исходный checkout не меняется.
Стенд слушает только `127.0.0.1:8001`; после остановки временная копия удаляется.

Используются настоящие formats, ladder search/match, подготовка Random Battle,
симулятор и WebSocket-протокол. Настройки локального стенда:

- локальная ladder; loginserver указывает на неиспользуемый loopback-порт;
- сняты гостевые, IP и частотные ограничения, порог обязательной регистрации;
- только для имён `delay*` добавлена задержка 1200 мс перед настоящим `prepBattle`;
- только для `shared*` пустая тестовая assertion получает признак зарегистрированного
  пользователя, чтобы штатный сервер объединил два соединения.

Последние два пункта — контролируемые тестовые вмешательства. Сетевые сообщения
search/match не подменяются, но этот стенд **не проверяет** подписи assertion,
публичную регистрацию, ограничения по IP, публичный рейтинг и пороги регистрации.
Его настройки нельзя переносить на публичный сервер.

## Тестовая личность клиента

`MatchmakingController.localTestUserId` принимается только с обоими флагами
`SHOWDOWN_LOCAL=true` и `SHOWDOWN_MATCHMAKING_TEST=true`, вне product-сборки.
Личность становится пригодной для теста только после совпадающего named updateuser
на разрешённом локальном `ws` endpoint. При смене личности или поколения соединения
старые действия недействительны. На публичном `wss` этот обход не работает.
`MyApp` параметр не передаёт; AuthController и публичный HTTP-вход не изменены.

На свежем сервере первое присвоение имени отправляет updateuser, но не новый
updatesearch. Клиент намеренно не использует гостевой снимок как состояние аккаунта.
Поэтому helper сначала создаёт имя, затем переподключается: штатное восстановление
существующей личности присылает актуальный снимок. Это явная подготовка теста,
не автоматически добавленный reconnect приложения. После входа без нового снимка
пользователю также может понадобиться переподключение и повторный вход.

## Что проверяют сценарии

`test/integration/local_matchmaking_test.dart`:

- два независимых сокета: очередь → пустой снимок → init → приватный request,
  присутствует games; один и тот же battle ID у обоих клиентов;
- requestRevision равен числу полученных request; ровно `/utm null` и
  `/search gen9randombattle`, без повторного join/leave;
- переподключение к существующей игре блокирует новый поиск;
- адресная отмена до завершения prep не является ACK: поздняя очередь вызывает
  ровно одну дополнительную отмену, затем stoppedObserved → outcomeUnknown;
- новый поиск после reconnect действительно отправляется, попадает в очередь
  и отменяется; одно лишь состояние доступной кнопки не считается проверкой;
- второе соединение синтетического зарегистрированного аккаунта видит общую
  очередь и отмену первого, но не получает токен чужой попытки.

`test/features/matchmaking/local_identity_test.dart` проверяет закрытый по умолчанию
обход, локальный endpoint, отказ на публичном endpoint и инвалидирование личности.
Сетевые тесты без явных флагов пропускаются.

`integration_test/local_matchmaking_app_test.dart` строит настоящий ConnectionScreen,
включает экспериментальный режим через переключатель, нажимает поиск и проверяет
единственный BattlePanel найденного боя и приватный request. Второй клиент работает
в том же процессе через отдельный реальный сокет. Авторизация в UI не тестируется.

## Воспроизведение

Нужны Node.js 22+, Git, tar, Flutter из проекта и зависимости сборки целевой платформы.
В отдельном checkout официального `smogon/pokemon-showdown`:

```sh
git checkout b354a81f11003a03f0dcd1dafd4edc641e6763bd
npm ci
```

Из этого проекта, в отдельном терминале:

```sh
SHOWDOWN_PATH=/absolute/path/to/pokemon-showdown node tool/local_matchmaking_server.cjs
```

Дождаться `Worker 1 now listening on 127.0.0.1:8001`, затем:

```sh
flutter test test/integration/local_matchmaking_test.dart test/features/matchmaking/local_identity_test.dart --dart-define=SHOWDOWN_LOCAL=true --dart-define=SHOWDOWN_MATCHMAKING_TEST=true
flutter test integration_test/local_matchmaking_app_test.dart -d linux --dart-define=SHOWDOWN_LOCAL=true --dart-define=SHOWDOWN_MATCHMAKING_TEST=true
flutter test integration_test/local_matchmaking_app_test.dart -d emulator-5554 --dart-define=SHOWDOWN_LOCAL=true --dart-define=SHOWDOWN_MATCHMAKING_TEST=true
```

Android-эмулятор использует `10.0.2.2`, Linux — `127.0.0.1`. Для физического Android
этот helper не предназначен. Запуски последовательные; имена получают уникальный
суффикс. После проверки остановить сервер Ctrl+C и свой эмулятор.

Сетевой набор повторён после экспорта и сборки чистой закреплённой ревизии.
Сборки в строках UI — именно тестовые приложения с явными development-флагами,
не release-сертификация. Стандартные сборки дополнительно проверяет существующий CI.

Эта приёмка доводит поиск до первого приватного запроса; полный случайный бой,
все механики, публичная авторизация/регистрация и фактическое изменение публичного
рейтинга здесь не проверялись. Для них требуется отдельная приёмка. Экспериментальный
режим остаётся выключенным по умолчанию. Обычный CI проверяет регрессии и сборки;
живой локальный набор запускается явно по приведённым командам.
