## Команды

Все команды глобальные, без ID комнаты. Полные сообщения WebSocket:

| Действие | Сообщение | Подтверждение |
|---|---|---|
| Подготовить случайную команду | `\|/utm null` | Отдельного ACK нет; это строка `null`, не JSON null |
| Начать поиск | `\|/search gen9randombattle` | Снимок с форматом либо появление собственной игры; send не ACK |
| Отменить свой формат | `\|/cancelsearch gen9randombattle` | Свежий снимок; если поиска уже нет, адресная команда может не дать ответа |

Перед каждым новым поиском последовательно отправляются `/utm null`, затем
`/search gen9randombattle` в одном актуальном connectionEpoch. Если первая отправка
не удалась, вторую не выполнять. Если результат второй неизвестен, не повторять.
Обе команды не образуют серверную транзакцию. Формат берётся из allowlist и
текущего каталога; не сериализовать пользовательский текст, русское название,
custom rules, разделители или переводы строк.

Сервер также поддерживает `/cancelsearch` без аргумента и `/search` без аргумента:
они отменяют все поиски аккаунта. Клиент выбирает адресную отмену, чтобы не
затрагивать поиски другого формата в другой сессии. Если другой клиент ищет тот
же формат, разделить владельцев на сервере невозможно; UI должен объяснять это.

## Каталог форматов

Глобальная строка `|formats|...` заменяет прежний каталог текущего соединения.
`|,1|S/V Singles|[Gen 9] Random Battle,4f` — синтетический пример секции и записи.
`,LL` означает локальный ladder; это не формат. `,<decimal column>` и следующая
строка-сегмент обозначают секцию. Пустой сегмент-маркер секции поддерживается
клиентом C1. Название секции не канонический formatId.

Современная запись: `<name>,<hex flags>`, разделение по последней запятой.
Канонический ID: ASCII lowercase с удалением всего кроме `a-z0-9`.
`[Gen 9] Random Battle` → `gen9randombattle`.

| Маска | Значение |
|---|---|
| 0x1 | Команда предоставляется форматом |
| 0x2 | Доступен поиск |
| 0x4 / 0x8 | Доступен challenge / tournament |
| 0x10 | Уровень 50 |
| 0x20 | Устаревший partner/multi-флаг; этот режим не поддержан |
| 0x40 | bestOfDefault — настройка challenge UI, сама по себе не включает серию при `/search` |
| 0x80 / 0x100 | teraPreviewDefault / itemClauseDefault |

В S2 флаг 0x20 больше не выставляется; C1 ещё понимает его. В S6 у целевого
формата есть bestOfDefault: нельзя ошибочно отвергать обычный поиск из-за 0x40.
Флаги не содержат общего надёжного признака rated. Для целевого формата показывать
«рейтинговый поиск; сервер может отключить начисление рейтинга», не обещать
нерейтинговый бой. Unrated Random Battle — другой ID, вне allowlist этого этапа.

Политика нашего декодера (строже permissive JS-разбора): hex целиком валиден;
пустое имя/ID, дубликат канонического ID, повреждённый маркер или обрыв секции
делают снимок malformed. Не использовать прежний каталог для запуска после
malformed-обновления. Неизвестные биты сохраняются, запись помечается unsupported
и не разрешает поиск; остальные корректные записи остаются доступными.
Старые суффиксы `,#`, `,,`, `,` и записи без кода распознаются как legacyUnsupported,
но не дают доступности: полная обратная совместимость не нужна этому этапу.
Пустой каталог валиден и означает отсутствие доступных форматов.

Доступность целевого формата = свежий валидный каталог + точный ID + random/preset
+ searchShow + поддержанная маска/режим + включённый тестовый режим клиента.
Повреждение/удаление каталога во время поиска запрещает новый старт, но не мешает
отменить уже отправленный поиск или принять собственную найденную комнату.

## Снимок поиска

Глобальная строка `|updatesearch|JSON` содержит:

- `searching`: массив канонических ID всех текущих поисков аккаунта;
- `games`: null или объект `roomId: title` всех текущих игр, включая не-Pokémon;
- дополнительные поля допустимы и не меняют известную семантику.

Нет attemptId, rqid, результата конкретной команды или признака «это ответ на
отмену». Каждый валидный снимок заменяет предыдущий. Пустой объект games допустим.
Наш декодер требует оба поля; не приводит типы, отклоняет дубликаты searching,
невалидные ID, нестроковые заголовки, массив вместо games и повреждённый JSON.
Ошибочное сообщение не превращается в пустой список и не подтверждает отмену.
Комнатные formats/updatesearch не меняют глобальное состояние.

Заголовки — недоверенный текст, не HTML и не команды. S3 может добавлять `*` к
названию; это не часть roomId. `games` не доказывает, что игра появилась от нашего
поиска: она могла существовать ранее либо начаться в другом клиенте.

## Условия запуска и состояния

Начальный baseline: валидный снимок текущего соединения без поисков и игр.
Для публичного UI требуется подтверждённый существующий аккаунт через текущий
AuthController. Это политика продукта, а не утверждение, что сервер всегда
требует зарегистрированный аккаунт: C1 проверяет named, S4 имеет дополнительные
настраиваемые ограничения регистрации/ранга. В локальном полном сервере допустима
отдельная тестовая named-личность без отправки публичных credentials на localhost.

Перед стартом повторно проверять epoch, личность, каталог, baseline, отсутствие
ручного join/leave, активного боя и незавершённой попытки. Смена личности делает
попытку неопределённой; не отменять поиск уже от имени другого пользователя.

| Состояние | Смысл / действия |
|---|---|
| unavailable | Нет обязательных условий; старт запрещён |
| idle | Свежий baseline, нет активной попытки; можно явно начать |
| submitting | Команды отправлены; ждём свидетельства сервера, старт запрещён |
| searching | Формат присутствует в свежем searching; разрешена отмена |
| cancelling | Отмена запрошена, результат ещё не установлен |
| stoppedObserved | В свежем снимке нет формата, но это не доказательство окончательной отмены |
| awaitingBattle | Есть кандидат собственной игры, ждём init/сведения о стороне |
| inBattle | Владелец принял одну подтверждённую боевую комнату |
| outcomeUnknown | Таймаут/ошибка/неоднозначность; новый старт и автоповтор запрещены |
| disconnected | Снимки устарели, действий нет; переподключение не повторяет поиск |

Имена состояний — контракт, не уже существующие Dart enum.
`stoppedObserved` показывает «Поиск отсутствует в последнем ответе; проверяем,
не создан ли бой», а не «Отмена успешно завершена». До разрешения неоднозначности
новый поиск запрещён. Произвольный debounce или таймаут не является ACK.
В этом консервативном прототипе отсутствие последующих данных приводит к
outcomeUnknown; пользователь может отключиться и восстановить свежую сессию.
Разрыв сам по себе не доказывает отмену на уровне аккаунта. Повторный старт после
восстановления допустим только после нового baseline; существующие игры/поиски
блокируют его. Живая приёмка должна проверить позднюю подготовку старого поиска.
Если для удобного повторного поиска понадобится надёжный барьер синхронизации,
его нужно отдельно подтвердить полным сервером; этот PR его не выдумывает.

## Гонки и переходы

1. Двойной старт или старый callback ничего не отправляет. Локальные attemptToken,
   epoch, identityRevision и sequence защищают только клиентские операции;
   сервер не возвращает attemptToken. Уже принятые, но ещё не доставленные события
   должны блокировать отправку, как у контроллера боевых решений.
2. Успех send не переводит в searching. Немедленный матч может появиться без
   searching=[format]. Пустой searching без games после старта ещё не отказ.
3. Отмена в submitting: сохраняем намерение и отправляем одну адресную отмену.
   Если затем впервые приходит searching=[format], отправляем одну дополнительную
   адресную отмену для поздней постановки в очередь. Дубликаты того же состояния
   не создают цикл команд. Если сначала пришёл пустой снимок, не снимаем намерение.
   Таймаут без подтверждения очереди/комнаты → outcomeUnknown.
4. S3 ждёт async prepBattle, а cancelSearch удаляет только уже существующую запись.
   Поэтому ранняя отмена не доказана окончательной. Это вывод из исходников;
   возможность доставки конкретной последовательности нужно проверить живьём.
5. S2 перед созданием комнаты отменяет поиски и отправляет пустой снимок. Комната
   может прийти после пустого снимка/клика отмены. Собственная подтверждённая игра
   имеет приоритет: открыть бой, не посылать автоматический leave/forfeit.
6. popup/error не содержит идентификатора попытки и может быть предупреждением
   (например, ladder disabled), после которого бой всё же создаётся. Показать
   безопасную категорию, сохранить ожидание/неопределённость; не считать любую
   popup окончательным отказом и не запускать поиск повторно.
7. Разрыв/смена личности/epoch запрещает повтор команды. События старого epoch
   игнорируются. Старый список games нового соединения не считается новым матчем.
8. Внешний поиск или несколько games блокируют новый старт. Не отменять чужие
   форматы, не выбирать одну из нескольких комнат произвольно. Один локальный
   владелец не гарантирует, что сервер не создаст второй бой в другом клиенте.

## Передача комнаты без потери событий

Единственный владелец комнат резервируется до `/search`. Сейчас ConnectionController
отправляет leave для неожиданного init; в PR 4 это необходимо изменить.
ShowdownSession не переигрывает события для поздних подписчиков: владелец должен
получать поток заранее и передать init, историю и первый request ровно один раз.
Сохранить существующие epoch/sequence-ограничения BattleDecisionController.

Кандидат — новая запись games с battle-ID либо battle init во время попытки.
До подтверждения принадлежности это не активный бой: нужен games с тем же ID,
init|battle и подтверждение своей стороны текущей личностью через player/request.
Проверка формата/Gen 9 singles и совместимости остаётся в боевом слое.
Порядки games→init и init→games должны работать; последний — защитный сценарий,
не утверждение о порядке на закреплённом сервере. Не посылать лишний join для
автоматически присоединённого боя. Повтор init не создаёт второй контроллер.

События кандидата до games буферизуются ограниченно: политика этого этапа —
не более 256 событий и 256 KiB UTF-8 суммарного исходного текста на одну комнату,
таймаут ожидания 10 секунд (инъецируемый для тестов). Превышение любого лимита
не теряет события молча: outcomeUnknown, выбор заблокирован. Буфер освобождается
после передачи/разрыва/dispose. Второй кандидат вызывает конфликт, не замену.
Неизвестный request или неподдержанные механики могут заблокировать уже принятый
бой; это не причина объявлять поиск неуспешным или искать ещё одного соперника.

## Корпус, проверки и передача следующим PR

[messages.json](../test/fixtures/matchmaking/messages.json) — входы декодеров;

Синтетический request использует существующий корпус боя, не случайную команду.

В этом PR проверяется целостность спецификации, не поведение отсутствующих
контроллеров. PR 2 подключит formats-примеры к реальному декодеру; PR 3 —
updatesearch и команды; PR 4–5 — сценарии к владельцу/контроллеру;
PR 6 — UI RU/EN; PR 7 — полный локальный сервер, два клиента и Android/Linux.
Тесты должны подавать входы в production-код и сравнивать фактический результат,
а не выдавать чтение expect за пройденный сценарий.

Обязательная живая приёмка: async prep/cancel, пустой снимок перед боем,
адресная отмена отсутствующей очереди, порядок games/init/request, другой клиент
того же аккаунта, повторный поиск после отмены/разрыва, реальная регистрация/ранг.
Для двух локальных клиентов отдельно проверить серверные IP-ограничения
matchmaking; тестовые настройки не переносить на публичный сервер.
Текущий local_battle_server.cjs не содержит матчмейкинга и эти проверки не заменяет.
