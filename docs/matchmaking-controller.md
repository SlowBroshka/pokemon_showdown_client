## План и результат

этот компонент не создаёт. Приложение подключит его в PR 6.

## Составление зависимостей

Создать один AuthController, FormatCatalogController и RoomOwner, затем один
MatchmakingController **до подключения** общей ShowdownSession. Конструктор
проверяет, что все зависимости используют тот же объект сессии, и что таймаут
положителен. Использовать `ConnectionController.rooms`; не создавать второго
владельца. Поздние подписчики не получают историю сессии.

Контроллер предоставляет `state`, `changes`, `canStart`, `canCancel` и
`experimentalEnabled`. По умолчанию экспериментальный режим выключен.
`MatchmakingState` содержит phase, непрозрачный attemptToken и безопасную notice.
Произвольный текст popup, исключений и credentials не сохраняется в состоянии.
Каталог по-прежнему предоставляет причины недоступности формата.

Вызвать `captureStart()` при формировании действия UI, затем `start(action)`.
Action привязан к экземпляру контроллера, epoch, source sequence и снимку
подтверждённой личности. Любое продвижение источника делает старое действие
непригодным; UI получает новый action при обновлении. `cancel(state.attemptToken)`
отменяет только текущую попытку. Старый token не отменит новый поиск после reconnect.

`start`/`cancel` возвращают true при принятии команды локальным транспортом,
**не при подтверждении сервером**. False означает, что действие не завершилось
локально; при ошибке send доставка может быть неопределённой. Решение о повторе
нельзя принимать по одному bool: нужно читать state. Автоматических повторов нет.

## Условия запуска

Нужны connected и текущий epoch, authenticated в AuthController, разрешённый
`gen9randombattle` в свежем каталоге, экспериментальный режим, свободный RoomOwner
и валидный пустой глобальный updatesearch. Baseline должен быть получен после
подтверждения текущей личности. Гостевой снимок до авторизации не разрешает поиск.
Публичный named без подтверждения аккаунта не допускается. Обход авторизации для
локального сервера не добавлен; его отдельный тестовый путь относится к PR 7.

Проверки используют watermark источника и барьер завершения доставки frame.
Уже полученные, но ещё не доставленные изменения не могут разрешать отправку.
RoomOwner резервируется раньше utm/search. После синхронных уведомлений владельца
и между двумя send условия проверяются снова. `ownsSearch(token)` проверяет,
что резервирование по-прежнему принадлежит этой попытке.

Если utm не принят, search не отправляется. Если условия изменились между командами,
резервирование консервативно остаётся заблокированным до переподключения.
При исключении transport сам разрывает соединение: состояние становится disconnected
с notice sendFailed. Это не доказательство отсутствия серверной операции.

## Переходы и отмена

| Состояние | Значение |
|---|---|
| unavailable | Условия запуска не выполнены |
| idle | Можно захватить действие и явно начать |
| submitting | Команды приняты локально; подтверждения очереди ещё нет |
| searching | Целевой формат наблюдался в updatesearch |
| cancelling | Адресная отмена отправлена; результата ещё нет |
| stoppedObserved | Формат отсутствует в последнем снимке; возможен создающийся бой |
| awaitingBattle | RoomOwner ожидает доказательства одного кандидата |
| inBattle | RoomOwner принял собственную комнату |
| outcomeUnknown | Ошибка, конфликт или истекшее ожидание; повторный старт закрыт |
| disconnected | Соединение неактуально, отправок нет |

Ранняя отмена в submitting отправляет одну `/cancelsearch gen9randombattle`.
Если после неё впервые наблюдается очередь целевого формата, допускается ровно
одна дополнительная отмена. Она отправляется после доставки всего frame:
появившаяся в том же пакете комната подавляет отмену. Повторы снимка и переходы
через пустой список не создают цикл команд. Общая отмена без formatId не используется.
Сервер не различает два клиента одного аккаунта, ищущих тот же формат.

Пустой список не освобождает резервирование. responseTimeout (по умолчанию
10 секунд) ограничивает ожидание ответа после отправки и неоднозначное отсутствие
очереди. Явная отмена начинает свой срок ожидания. Повторные пустые снимки и
поздняя очередь не продлевают его. Подтверждённая очередь без отмены может ждать
соперника неограниченно; таймаут принятия кандидата принадлежит RoomOwner.

После таймаута исхода собственная подтверждённая игра всё ещё может быть принята,
если RoomOwner не обнаружил конфликт и не исчерпал срок/лимиты кандидата.
Подтверждённая комната имеет приоритет над отменой. Контроллер не посылает join,
leave или forfeit; сохранение первого request остаётся обязанностью RoomOwner.
После явного выхода из найденной комнаты эта попытка не разрешает повторный поиск:
в прототипе нужен reconnect и новое подтверждение условий.

Popup/error — только serverNotice, не окончательный отказ. Повреждённый updatesearch
даёт invalidSearchSnapshot и outcomeUnknown, согласованно с RoomOwner из PR 4.
Сценарий malformed-does-not-cancel исправлен: прежнее ожидание cancelling
противоречило реализованной строгой обработке владельца. Каталог, исчезнувший после
отправки поиска, не блокирует отмену или принятие комнаты. Смена личности исключает
команды; AuthController также может отключить сессию по своим правилам.

## Очистка и восстановление

`dispose()` идемпотентен, отменяет подписки и таймеры, удаляет listener владельца.
Он не уничтожает общую сессию/auth/catalog/rooms и не отправляет отмену. Оставшийся
неопределённый резерв удерживает RoomOwner: уничтожение UI не является ACK сервера.
Владелец продолжает принимать уже начавшийся бой. При уничтожении всей композиции
сначала дождаться dispose контроллера поиска, затем освобождать зависимости.

Connecting сбрасывает попытку даже при немедленном reconnect, когда старый
disconnected уже недоступен. Старые epoch и токены не применяются к новой сессии.
Новый поиск требует новой авторизации, каталога и baseline; автоматического
восстановления поиска нет.

## Проверки

45 новых тестов: 22 упорядоченных сценария scenarios.json исполняются через
MatchmakingController, AuthController, FormatCatalogController, RoomOwner и
настоящий ShowdownSession с тестовыми WebSocket/HTTP. Исполнитель поддерживает
явно перечисленные сценарии, сравнивает фактические фазы, команды, доступность,
комнату и категории notices. Остальные случаи не объявляются исполненными этим
интерпретатором: сложные гонки, ошибки и первый request проверяются отдельными
тестами, ограничения кандидата — тестами PR 4.

Дополнительные проверки: порядок резервирования/send, старые действия,
авторизация и baseline, экспериментальный режим, ручной вход, отказ обеих команд
и отмены, изменение условий между send, frame с очередью и игрой, непродление
таймаута, поздний матч, переподключение и dispose. Тестовый sink получил callback
для моделирования ошибки конкретной команды и изменения условий между send.

Живой поиск на публичном или полном локальном сервере не запускался.
Платформенные сборки выполняет CI. PR 6 добавляет UI RU/EN; PR 7 проверяет реальную
async prep/cancel, два клиента и Android/Linux.

Итог проверки: полный `flutter test` — **425 passed**, 2 opt-in сетевых теста
пропущены; `flutter analyze` — без замечаний.
