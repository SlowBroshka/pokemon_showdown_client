# Протокол поиска: план и API третьего PR

Дата: **29 октября 2026 года**. Задача [#41](https://github.com/SlowBroshka/pokemon_showdown_client/issues/41).
Основа — [контракт поиска](matchmaking-contract.md) и [каталог форматов](format-catalog.md).

## План и исполнение

1. Добавить отдельные типизированные команды подготовки random team, поиска и
   адресной отмены с проверкой аргументов до сериализации.
2. Определить неизменяемый снимок всех поисков/игр аккаунта и отдельный результат
   ошибки, который нельзя спутать с пустой очередью.
3. Разбирать updatesearch строго: обязательные поля, типы, ID, дубликаты searching;
   сохранять неизвестные форматы/игры, разрешать дополнительные JSON-поля.
4. Интегрировать UpdateSearchEvent в общий декодер только в глобальной области;
   не превращать ошибки/уведомления и пустые снимки в подтверждения команд.
5. Исполнить все 17 updatesearch-примеров корпуса через production-декодер,
   проверить команды, неизменяемость и доставку через общую сессию.
6. Выполнить форматирование, анализатор, полный набор тестов; оформить PR.

Реализованы пункты 1–5; результаты проверок ниже. Код не начинает поиск сам:
контроллер, владелец найденной комнаты и UI — следующие PR. Не добавлялись
новые подписки приложения, таймеры поиска или отдельный транспорт.

## Исходящие команды

Все классы доступны через core/protocol/client_commands.dart и реализуют ClientCommand.

| Класс | Аргументы | Полное сообщение serialize() |
|---|---|---|
| PrepareRandomTeamCommand | Нет; const constructor | `\|/utm null` |
| SearchBattleCommand | required formatId | `\|/search gen9randombattle` |
| CancelSearchCommand | required formatId | `\|/cancelsearch gen9randombattle` |

formatId должен точно равняться gen9randombattle. Пустая строка, пробелы, другой
регистр, название формата, custom rules, другие форматы и разделители отклоняются
ArgumentError без включения входного значения в ошибку. Это ограничение текущего
этапа, а не ограничение протокола сервера. Расширение allowlist требует отдельной
приёмки новых форматов. Аргумент у отмены обязателен: отмена всех поисков аккаунта
через этот API невозможна.

`null` в первой команде — буквальный текст протокола. Сериализация не отправляет
данные, не проверяет авторизацию/каталог и не подтверждает постановку в очередь.
Будущий контроллер проверяет доступность и отправляет подготовку, затем поиск
через ShowdownSession.send с захваченным connectionEpoch. Это не атомарная пара;
при ошибке первой отправки вторую выполнять нельзя. Оркестрация этой пары и
обработка неопределённого результата принадлежат будущему контроллеру, а не PR 3.

## Входящие данные

`decodeSearchSnapshot(data)` принимает JSON после updatesearch| и возвращает
SearchSnapshotResult. `isValid=true` означает только корректность данных;
`snapshot` содержит SearchSnapshot. При ошибке isValid=false и snapshot=null:
нет пустого списка, который мог бы ложно подтвердить прекращение поиска.

SearchSnapshot содержит:

- `List<String> searching` — все канонические ID поисков, в порядке сервера;
- `Map<String, String>? games` — все игры аккаунта и их заголовки.

Список и карта копируются и закрыты для изменений. `games: null` и `{}` сохраняются
как разные валидные значения. Снимок не содержит derived-флагов вроде cancelled,
matched или accepted. Такие выводы требуют истории и контекста контроллера.

Правила валидации:

- Верхний уровень — JSON-объект, оба поля обязательны.
- searching — массив строк, каждая непустая и содержит только a-z0-9;
  дубликаты запрещены. Никакого приведения типов/нормализации входных ID.
- games — null или объект. Ключи непустые, только a-z0-9 и дефис, как в текущем
  контракте комнат клиента; значения — строки. Массив вместо объекта запрещён.
- Дополнительные поля допустимы и игнорируются. Неизвестные форматы, несколько
  поисков, небоевые игры и несколько комнат сохраняются без фильтра allowlist.
- Заголовки сохраняются буквально, включая пустую строку, HTML-подобный текст,
  переводы строк внутри JSON и завершающий `*`. Они не являются командами,
  HTML или доказательством принадлежности игры нашей попытке.

`UpdateSearchEvent` публикует `result` и исходный ServerRecord. Глобальный
updatesearch с повреждённым JSON тоже создаёт этот тип события: будущий потребитель
должен отозвать доверие к прежнему снимку, не принимать ошибку за отсутствие игр.
Комнатный updatesearch даёт MalformedServerEvent, не UpdateSearchEvent.
Исходная запись может содержать приватные сведения; безусловное логирование
не добавлено. Сообщения popup/error остаются отдельными типами событий.

## Проверки и границы

Добавлено **27 тестов**: 17 примеров корпуса и 10 дополнительных проверок.
Проверяются реальные декодер/сериализаторы, типы событий, коллекции, внешние
поиски и заголовки, null/пустые/повреждённые значения, инъекции, доставка трёх
последовательных снимков в одном frame без автоматического ответа и запрет
отправок через отключённое либо старое соединение. Сокет в тестах подставной.

Полный набор: **358 passed**, 2 opt-in сетевых теста пропущены; flutter analyze
без замечаний. Живые матчи и локальные платформенные сборки не запускались;
сборки Android/Linux остаются существующему CI.

Все 34 примера messages.json теперь проверяют производственные декодеры
(17 formats + 17 updatesearch). **34 сценария scenarios.json по-прежнему являются
спецификацией будущих контроллеров**: этот PR не объявляет их пройденными.
Пустой searching не ACK отмены, send не ACK поиска, а games не связывает комнату
с локальным attemptId. Гонки и правила принятия комнаты остаются в контракте.
